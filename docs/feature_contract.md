# Контракт признаков и порядка событий (`OnlineFeatureStore` & `/score`)

Документ фиксирует единые правила расчёта признаков, времени, граничных случаев и порядка событий для офлайн-обучения (`src/features/engineering.py`) и онлайн-скоринга (`src/api/app.py`, `src/features/online_store.py`).

## 1. Временная зона и представление времени

- **Каноническая временная зона:** `UTC` (`datetime.timezone.utc`).
- **Наивные `datetime` (без `tzinfo`):** трактуются как `UTC` (никогда не зависят от локального часового пояса ОС сервера).
- **`datetime` со смещением (`+03:00`, `+05:00`, `Z`):** приводятся к `UTC` через `.astimezone(timezone.utc)` до расчёта epoch-секунд, `hour_of_day` и `is_night` (`00:00–05:59 UTC`).
- **Отсутствие `timestamp` (`None`):** используется детерминированный якорь `2026-01-01T00:00:00Z + timedelta(hours=step)`.

## 2. Семантика типов операций (`type`) и мерчантов

| Тип операции | Движение средств | Трактовка признаков и состояния |
|---|---|---|
| `TRANSFER` | Списание `Orig` → зачисление `Dest` | Полный учёт `balance_drain_ratio`, `orig_balance_zero_after`, `orig_balance_error`, `dest_balance_error`, исходящих окон `1h/24h/7d`, статистики Welford и P2P-графа (`dest_in_degree`, `is_mule_candidate` для не-мерчантов). |
| `CASH_OUT` | Снятие/вывод средств `Orig` | Списание со счёта отправителя; если баланс `Dest` не изменился (`oldbalanceDest == newbalanceDest` для банкомата/агента), `dest_balance_error = 0.0`. Учитывается в исходящих окнах и графе вывода. |
| `PAYMENT` | Оплата товаров/услуг мерчанту | Списание у отправителя и учёт в исходящей активности клиента, но **не формирует признак P2P-дроппера** (`dest_in_degree = 0`, `dest_tx_count_24h = 0`, `is_mule_candidate = 0.0`). При ненаблюдаемом балансе мерчанта (`0.0 -> 0.0` или `nameDest` с префиксом `M`) `dest_balance_error = 0.0`. |
| `CASH_IN` | Входящее пополнение счёта `Orig` | Не является списанием: `balance_drain_ratio = 0.0`, `orig_balance_zero_after = 0.0`, `orig_balance_error = \|(oldbalanceOrg + amount) - newbalanceOrig\|`, `dest_balance_error = 0.0`, `amount_zscore = 0.0`, `amount_to_mean_ratio = 1.0`. Обновляет отпечаток устройства и время последней активности клиента, **не загрязняя** исходящие окна переводов и граф получателей. |
| `DEBIT` | Прямое дебетовое списание | Учитывается как исходящее списание отправителя аналогично `TRANSFER` (с исключением мерчантов `M*` из графа дропперов). |

## 3. Отсутствие истории (Cold Start)

Для нового отправителя (ранее не встречался в истории):
- `orig_past_tx_count = 0.0`, все `orig_tx_count_* = 0.0` и `orig_tx_sum_* = 0.0`;
- `amount_zscore = 0.0`, `amount_to_mean_ratio = 1.0`;
- `is_new_recipient = 0.0`, `is_new_device = 0.0` (первичная регистрация базового профиля; смена устройства/получателя на последующих операциях даёт `1.0`);
- `time_since_last_tx_hours = 168.0` (априорная пауза 7 суток, диапазон `[0.0, 720.0]`).

## 4. Неизвестные поля и значения

- **Вход API (`TransactionRequest`, `FeedbackRequest`):** `extra="forbid"` — любые неизвестные или опечатанные поля отклоняются со статусом `HTTP 422`.
- **Прямой вызов `OnlineFeatureStore(..., strict_fields=True)`:** неизвестные ключи вызывают `UnknownFeatureFieldError`.
- **Неизвестные категории** (при прямом вызове вне enum): все one-hot индикаторы `type_*` / `channel_*` равны `0.0`. Отрицательные балансы, `amount <= 0` и `NaN`/`Inf` для обязательных числовых величин вызывают `FeatureStoreError`.

## 5. Правила порядка событий, повторов и одинакового времени

1. **Границы скользящих окон:** замкнутый интервал `[t - W, t]` по уже зафиксированным прошлым событиям с `prev_ts <= t` (`1h = 3600s`, `24h = 86400s`, `7d = 604800s`). Событие ровно на границе `t - W` включается в окно; событие на `t - W - 1s` вытесняется.
2. **Слишком старые события (`StaleEventError` → `HTTP 422`):**
   - отклоняются события отправителя старше `max_sender_out_of_order_seconds` (по умолчанию `300` сек) относительно последнего принятого события этого отправителя;
   - отклоняются события старше `max_global_staleness_seconds` (по умолчанию `86400` сек) относительно глобального watermark потока;
   - при малом сетевом джиттере в пределах допуска вставка в окна выполняется по `bisect`, сохраняя строгую отсортированность очередей и исключая заглядывание в будущее (`prev_ts > t` игнорируются).
3. **Повторы по `tx_id`:**
   - повтор с тем же `tx_id` и идентичными каноническими параметрами транзакции обрабатывается **идемпотентно**: состояние `OnlineFeatureStore` и БД повторно не изменяется, возвращается сохранённый результат (`is_duplicate=True`);
   - повторное использование `tx_id` с другими параметрами транзакции отклоняется (`DuplicateTransactionConflictError` → `HTTP 409 Conflict`).
4. **Одинаковое время (`t_1 == t_2`) для разных `tx_id`:**
   - в офлайн-пайплайне порядок детерминирован вторичным ключом `(utc_timestamp, tx_id)`;
   - в онлайн-скоринге запросы сериализуются через `RLock` в порядке поступления: второе событие видит состояние после фиксации первого (`time_since_last_tx_hours = 0.0`).
