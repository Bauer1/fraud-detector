# Эксплуатационный Runbook и процедура контролируемого выпуска модели

**Назначение:** регламент эксплуатации, теневого пилота, согласования релиза кандидатов, отката и реагирования на инциденты (Этапы 6–8 и Раздел 8 ТЗ).

## 1. Роли и ответственность

| Роль | Зона ответственности |
|---|---|
| **Владелец антифрод-сервиса (Product / Risk Lead)** | Утверждение порогов, матрицы стоимости, выпуск кандидатов (`POST /models/{version}/promote`) |
| **Дежурный инженер (On-Call MLOps / Backend)** | Доступность API, мониторинг задержки и fail-safe, экстренный откат (`POST /models/rollback`) |
| **Команда антифрод-аналитиков** | Разбор очереди `REVIEW`/`BLOCK`, выставление меток `fraud / not_fraud / unknown` с указанием `label_source` |

## 2. Жизненный цикл модели и запрет неконтролируемой публикации

1. **Обучение кандидата (`python -m src.training.pipeline` или `POST /retrain`):**
   - Создаёт неизменяемый каталог `models/registry/<version_id>/` с артефактами модели, калибратором, схемой признаков, снимком конфигурации и отчётом сравнения с текущим чемпионом (`comparison_report.json`).
   - **Никогда не перезаписывает** существующие версии и **не публикует** кандидата автоматически при вызове `/retrain` (`governance.auto_promote_on_retrain: false`).
2. **Проверка перед выпуском (`GET /models/{version_id}/report`):**
   - Проверить `guardrail_passed == true`: отсутствие просадки PR-AUC сверх допустимого порога и соблюдение лимита очереди `capacity_within_limit == true` на валидации.
   - Убедиться, что при обучении не использовались кейсы из отложенного тестового holdout (`is_independent_test == true`).
3. **Контролируемый выпуск (`POST /models/{version_id}/promote`):**
   - Требует указания `approved_by` и `reason`.
   - Текущая активная модель переводится в статус `superseded` и сохраняется в стеке `previous_active_versions` для мгновенного отката.
   - Горячая перезагрузка в памяти API не сбрасывает накопленное состояние `OnlineFeatureStore`.
4. **Откат (`POST /models/rollback`):**
   - Восстанавливает предыдущую утверждённую версию из `models/registry/` за секунды без переобучения и фиксирует событие `ROLLBACK` в журнале аудита реестра.

## 3. Проведение теневого пилота (Shadow Pilot, Этап 7)

1. Включить `scoring.shadow_mode: true` (или передавать `?shadow=true` из платёжного шлюза для выделенной доли трафика).
2. Проверить по `/health`, что `decision_mode == "SHADOW"`. В этом режиме все вызовы возвращают `effective_action = "ALLOW"`, но сохраняют расчётный `action` (`ALLOW/OTP/REVIEW/BLOCK`), факторы SHAP и задержку.
3. По истечении периода созревания меток (`monitoring.label_maturity_hours`) сверить:
   - фактический суточный объём `REVIEW` относительно лимита аналитиков;
   - долю перехваченного подтверждённого фрода и долю ложных `BLOCK`;
   - стабильность PSI и `p95/p99` задержки.
4. Переключить `shadow_mode: false` только после письменного подтверждения порогов владельцем риска.

## 4. Реагирование на алерты мониторинга (`/metrics/summary`)

| Код алерта | Причина | Действия дежурного / аналитика |
|---|---|---|
| `FAILSAFE_FALLBACK_INVOKED` | Ошибка ML/Feature компонента или превышение `scoring_timeout_budget_ms`; сервис перешёл на `fallback_policy` | Проверить `fallback_reason` в `GET /alerts`, логи контейнера; если проблема возникла после релиза новой модели — выполнить `POST /models/rollback`. |
| `ANALYST_REVIEW_CAPACITY_EXCEEDED` | Число кейсов `REVIEW` за 24ч превысило `max_daily_reviews` | Проверить всплеск сработавших правил и PSI по скору; при необходимости скорректировать порог `review` на валидации через выпуск нового кандидата. |
| `PSI_DRIFT_WARNING` / `PSI_DRIFT_CRITICAL` | Сдвиг распределения входных признаков или `risk_score` | **Не запускать слепой авто-релиз!** Проверить источник сдвига (новый канал, технический сбой поля, новая атака), дождаться зрелых меток (`fraud/not_fraud`), провести офлайн-оценку кандидата. |
| `LATENCY_P95_ABOVE_PROPOSED_SLA` | Рост `p95` времени ответа выше целевого ориентира | Проверить нагрузку на БД и размер окна/истории; убедиться, что `TreeExplainer` активен. |

## 5. Масштабирование и переход к промышленной инфраструктуре

Для промышленного контура с несколькими репликами API перед боевым запуском заменить прототипные локальные хранилища:
- `OnlineFeatureStore` (in-memory) → кластерное key-value/stream хранилище с персистентностью (Redis Cluster / RocksDB + Kafka/Flink point-in-time агрегаты);
- локальный `SQLite` (`data/fraud_agent.db`) → управляемый отказоустойчивый `PostgreSQL` с репликацией и политиками ретеншна PII.
