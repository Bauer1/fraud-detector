# Отчёт по проекту и верификации антифрод-сервиса (ТЗ v1.0)

> [!IMPORTANT]
> Приведённые ниже метрики получены на двух строго разделённых синтетических источниках — **исходном PaySim CSV** и **обогащённой симуляции проекта**. Они являются **smoke/benchmark-результатами прототипа** и **не подтверждают** качество на реальном банковском потоке до проведения теневого пилота на зрелых метках банка. Все бизнес-стоимости, пороги и лимиты очереди — проектные предложения (см. [docs/decision_and_cost_contract.md](../docs/decision_and_cost_contract.md)).

---

## 1. Целевая архитектура и выполненные требования ТЗ

Сервис оценивает риск перевода **до окончательной проводки**, выбирает действие `ALLOW`, `OTP`, `REVIEW` или `BLOCK`, сохраняет воспроизводимый снимок решения и поддерживает контролируемый жизненный цикл модели:

1. **Приём и защита от дубликатов (`src/api/app.py`, `src/data/schemas.py`, `src/security.py`)**:
   - Строгая валидация схемы (`extra="forbid"`), приведение времени к `UTC`, межсервисная аутентификация (`X-API-Key` / `Bearer`), sliding-window rate limit и опциональная HMAC-SHA256 псевдонимизация `nameOrig`/`nameDest`/`device_id`.
   - Идемпотентная обработка повторов по `tx_id` (`is_duplicate=True`) и отклонение конфликтующих дубликатов (`HTTP 409`).
2. **Контракт доступности признаков до решения (`src/features/online_store.py`, `docs/feature_contract.md`)**:
   - Исключены посттранзакционные балансы (`newbalanceOrig`, `newbalanceDest` → признаки `orig_balance_zero_after`, `orig_balance_error`, `dest_balance_error` исключены из модели) и запрещены поля утечки (`isFlaggedFraud`, `isFraud`, `chargeback` → `ForbiddenLeakageFieldError`).
   - Сырые идентификаторы служат только ключами point-in-time состояния и не передаются в ML.
   - Встроена наблюдаемость `cold_start_rate` и пропусков опциональных полей.
3. **Многоуровневый сервис решений и Fail-Safe (`src/agent/`, `src/models/supervised.py`)**:
   - Детерминированные правила (Level 1) → калиброванный на валидации GBDT (Level 2a, Platt scaling) + вспомогательный `IsolationForest` (Level 2b, ограничен сверху при отсутствии подтверждения от ML/правил — аномальный скор сам по себе никогда не вызывает `REVIEW` или `BLOCK`).
   - Подбор порогов `(t_otp, t_review, t_block)` на валидации по матрице затрат **с учётом суточного лимита аналитиков** (`max_daily_reviews`, `max_review_rate`).
   - Поддержка **теневого пилота** (`decision_mode="SHADOW"`, `effective_action="ALLOW"`) и детерминированного **fail-safe fallback** (`technical_status="DEGRADED_FALLBACK"` по политике `rules_only`).
4. **Аудит меток, зрелость и реестр моделей (`src/data/storage.py`, `src/models/registry.py`)**:
   - Трёхзначная разметка аналитика `fraud / not_fraud / unknown` с источником метки (`label_source`), периодом созревания (`label_maturity_hours`) и неизменяемым журналом `feedback_audit_log`.
   - Версионируемый реестр `models/registry/<version_id>/`: вызов `POST /retrain` обучает кандидата и формирует `comparison_report.json`, **не перезаписывая прошлые артефакты и не публикуя модель автоматически**. Выпуск и откат выполняются через `POST /models/{version}/promote` и `POST /models/rollback`.

## 2. Профилирование и строгое разделение источников данных

Происхождение, контрольные суммы SHA-256 и статистика зафиксированы в `models/manifests/`:

| Характеристика | Источник 1: Исходный PaySim CSV (`paysim_csv`) | Источник 2: Обогащённая симуляция проекта (`enriched_simulation`) |
|---|---|---|
| Файл и SHA-256 (префикс) | `data/paysim dataset.csv` (`16910f90577b0d98...`) | `data/raw/transactions.parquet` (`21a43d15cbc0df2e...`) |
| Полный объём источника | **6 362 620** строк (470.7 МБ) | **30 000** строк |
| Целевой класс `isFraud` | **8 213** (`0.1291%` — сильный дисбаланс; только в `TRANSFER` и `CASH_OUT`) | **450** (`1.5000%`, 5 сценариев + поздний concept drift) |
| Поле `isFlaggedFraud` | `16` срабатываний (всего `0.19%` полноты; **исключено из входов ML**) | Отсутствует |
| Отсутствующие поля телеметрии | **Нет** `tx_id`, `timestamp`, `device_id`, `channel`, `ip_country` | Присутствуют синтетические `tx_id`, `timestamp`, `device_id`, `channel`, `ip_country` |
| Правило одинакового времени | `(step ASC, source_row_idx ASC)` через `PAYSIM_{row_idx:08d}` | `(utc_timestamp ASC, tx_id ASC)` |
| Строки с `amount <= 0` | `16` строк с `amount = 0.0` (отфильтрованы и задокументированы в manifest) | `0` |
| Доля Cold Start по `nameOrig` | **99.998%** (почти все отправители встречаются однократно) | **2.00%** (600 клиентов с историей за 30 суток) |
| Число pre-decision признаков | **25** (`PAYSIM_PRE_DECISION_FEATURE_NAMES`) | **32** (`ENRICHED_PRE_DECISION_FEATURE_NAMES`) |

**Ключевые инженерные выводы по исходному PaySim CSV:**
- Из-за `99.998%` cold-start по `nameOrig` поведенческие окна отправителя в исходном PaySim практически пусты; высокий PR-AUC GBDT объясняется исключительно синтетическим правилом генератора PaySim (опустошение `oldbalanceOrg` в `TRANSFER`/`CASH_OUT`). Если в реальном банке `oldbalanceOrg` недоступен синхронно до авторизации, это качество **не воспроизведётся** — именно поэтому `oldbalanceOrg` выделен как условный атрибут контракта.
- Устойчивость по 4 хронологическим срезам Test: PR-AUC `mean = 0.9996 ± 0.0006` (95% bootstrap CI `[0.9950, 1.0000]`). Единственные 2 FP приходятся на холодных клиентов с крупным `CASH_OUT`. Задержка скоринга с SHAP: `p50 = 19.9 мс`, `p95 = 34.3 мс`, `p99 = 38.5 мс`.

### Устойчивость, сегменты, анализ FP/FN и задержка

- **Временные срезы и доверительный интервал:** 95% bootstrap CI для PR-AUC полного сервиса составляет `[0.9766, 0.9979]`; по 4 последовательным срезам Test `mean = 0.9857 ± 0.0138` (`min = 0.9698` на срезе с пиком новой схемы `novel_api_cashout`).
- **Вклад групп признаков (без утечки пост-балансов):** переход от транзакционных признаков к поведенческим окнам `1h/24h/7d` снижает FP/1000 для GBDT более чем в **4 раза** (`10.33 → 2.33`), а добавление P2P-графа и общих устройств дополнительно снижает FP/1000 до `1.83` (`1.00` у полного сервиса с правилами).
- **Сегментный разрез:** `CASH_OUT` PR-AUC = `0.9951`, `TRANSFER` PR-AUC = `0.9785`; канал `API` (концепт-дрейф) PR-AUC = `1.0000`, `WEB` = `0.9980`, `MOBILE` = `0.9700`; ночные операции (`00:00–05:59 UTC`) PR-AUC = `0.9955`.
- **Разбор ошибок на Test (6 000 операций):** всего `6` ложных тревог уровня `REVIEW/BLOCK` (`1 BLOCK`, `5 REVIEW` на сложных легитимных крупных переводах) и `1` пропуск `ALLOW` на сумму `1 800` (ранний шаг серии `velocity_burst`). Нагрузка очереди `REVIEW` составляет `2.1` кейса/сутки при проектном лимите `150`/сутки.
- **Задержка single-event скоринга с SHAP (локальный стенд):** `p50 = 66.5 мс`, `p95 = 78.3 мс`, `p99 = 157.2 мс`.
- **PSI-мониторинг:** зафиксирован ожидаемый сдвиг `CRITICAL` по `risk_score` (`PSI = 0.4940`) и `dest_in_degree` (`PSI = 0.3573`) из-за появления схемы `novel_api_cashout` в тестовом периоде. Согласно регламенту ([docs/runbook_and_release.md](../docs/runbook_and_release.md)), PSI направляет сигнал на расследование и проверку зрелых меток, а не на автоматическую публикацию модели.

## 5. Готовность к пилоту и оставшиеся шаги перед промышленным контуром

1. **Закрыть открытые вопросы владельца продукта/данных** по чек-листу в [docs/decision_and_cost_contract.md](../docs/decision_and_cost_contract.md) (валюта, синхронная доступность `oldbalanceOrg`, реальная матрица стоимости, SLA канала, окно созревания chargeback).
2. **Заменить локальные хранилища прототипа** (`in-memory OnlineFeatureStore` и локальный `SQLite`) на отказоустойчивое распределённое хранилище состояния (Redis/RocksDB + Kafka) и управляемую СУБД (`PostgreSQL`) для консистентности между репликами API.
3. **Провести теневой пилот (`shadow_mode: true`)** на реальном потоке канала с валидацией очереди аналитиков и качества на созревших метках перед включением боевых блокировок.
